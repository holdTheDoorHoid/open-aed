# aed-core

The rescue sequence for the fully automatic design (D-06), the supervisor's rules, the hardware interlock logic, the self-test order, the prompts and the event record.

**This code has only ever run against test mocks.** Nothing here has controlled real hardware or been connected to a person. The "hardware" in the tests is a crude simulated board: a capacitor that charges at constant power and empties through a resistor, a fake rhythm analyser and a fake shock planner. Passing tests show that the logic follows the rules below in that simulation. They do not show the device is safe. See [SAFETY.md](../../../SAFETY.md).

Every timing and limit is a provisional starting value in `src/config.rs`. None has yet been set from the resuscitation guidelines or from the defibrillator standard (IEC 60601-2-4), which has not been bought and read.

## How it is split

| Part | What it does |
|---|---|
| `config` | Every timing and limit, in one place, with the reasons |
| `hal` | Two separate lists of what each controller can see and do. The supervisor has its own clock, voltage sensor, pad reading, view of the cancel button, and its own fault alarm |
| `rescue` | The main controller's rescue sequence |
| `supervisor` | The second, independent controller. Shares nothing with the main controller except the status message |
| `interlock` | The hardware gate and the hardware rules (discharge by default; the charger cannot run while the discharge path is active; the shock sequence latch, time cap, permit cap and lockout of D-59; the test rail of D-61), written as rules for the simulator to copy and the circuit to be drawn to. They are plain logic on the real device, not software |
| `selftest` | The self-test order and time limits, including the interlock and bridge checks under the test permit (D-61) |
| `schedule` | The periodic self-tests while the device is off (D-15): when to run the daily low-voltage check and the weekly full-energy test, running one on the hardware, the test record, the capacitor-wear count and the ready indicator |
| `heat` | Temperature: the six sensor points, which readings to trust, the heat states (normal, warm, too hot, service needed), the charging limits, the pad heat total and the heat record (D-41, D-48, D-51, D-52) |
| `standby` | The device while "off": one wake handler for the heat record and the self-test schedule, the capacitor wear count (D-53), and what must survive the battery being taken out |
| `readiness` | The one readiness result that drives the ready indicator, with every reason |
| `export` | The record download by cable through the dock contacts (D-09): a versioned, checksummed text format |
| `prompts` | Every spoken or displayed message |
| `events` | The fixed-size event record |
| `link` | The two messages the controllers send each other |

### Invariants checked at every tick

`random_walks_never_break_a_safety_invariant` runs 400 repeatable random 90-second rescues (random rhythm changes, pad faults including pads just above the shock range, cancel presses, mode changes, and in 40% of runs one hardware fault such as a dead charger, a broken discharge load, a lost message wire, a wrong voltage sensor or a frozen main controller). At every 2 ms tick it checks:

1. A shock request is only raised when the last analyser decision was "shockable", the pads were in range and cancel was not pressed.
2. The bridge only fired with request, permit and both holds present.
3. The supervisor never gives a permit while letting go of the capacitor.
4. A frozen main controller is released by the supervisor within the heartbeat timeout, and the supervisor's own fault alarm is on within one more heartbeat period.
5. In the Fault state, and in every state that does not hold a charge, the charger is off and the main controller's hold is released.
5b. While a charge is being emptied in the background, the main controller neither holds nor charges.
5c. A background emptying is confirmed within its time limit, or the device is in the Fault state.
6. No state lasts longer than its time limit.

`exhaustive_single_disturbance_at_every_moment_of_an_armed_cycle_prevents_the_shock` applies each of seven disturbances at every 250 ms from the start of analysis to after delivery, and checks that no shock follows it. Rhythm changes get one analyser interval to be noticed.

## What the hardware must provide (D-59, D-60, D-61)

These are the requirements this firmware places on the circuit, at the level of the two hardware traits. They are for the hardware designer to check the circuit against. The pure rules are in `src/interlock.rs`, with a truth-table test for each; the simulator (`aed-sim`, `plant.rs`) models exactly these. Figures marked *proposed* are the simulator's model figures, not measurements.

1. **Start gate.** The interlock rail (`BRIDGE_5V`) rises only with the main controller's request AND the supervisor's permit AND both discharge paths held off AND no lockout (`sequence_may_start`). Removing any of them before the first conducting moment drops the rail at once, and nothing has happened.
2. **Sequence latch.** At the first conducting moment (the phase timer's first drive with the relay's position sense reading "bridge") the hardware latches SEQUENCE ACTIVE. From then the request, permit and hold lines are ignored until the last phase ends. The latch, the drivers and the over-current trip must stay powered through the pulse whatever the consent lines do (the review's R-1 turn-off order then never arises in normal use).
3. **The phase timer starts only with the relay on the bridge** (position sense stable), never into the front ends.
4. **Non-retriggerable time cap** from the first conducting moment (proposed 25 ms; the longest plan is 15.5 ms): drive is cut and the end latched, whatever the timer does, including a timer that keeps toggling (review R-4).
5. **Over-current trip** ends the sequence and is latched (§B6.4, 90 A).
6. **Permit-duration cap.** The rail may stay up without a sequence starting for at most a fixed time (proposed 250 ms, above the firmware's 200 ms permit window), then it is removed and locked out.
7. **Lockout, one sequence per permit.** After a sequence ends (or the permit cap), no new sequence until request, permit and test permit have all been absent together for a re-arm time (proposed 20 ms).
8. **Sequence status readable by each controller on its own input**: idle / armed (rail up) / active / ended-completed / ended-time-cap / ended-over-current / locked out by the permit cap (`SequenceStatus`).
9. **Patient relay position sense** readable by the main controller: front ends / bridge / neither. The relay returns the pads to the front ends when the rail drops, within about 10 ms (firmware allows 50 ms, `relay_return_timeout_ms`).
10. **Test permit line** from the supervisor (a third consent input). With the request and both holds it raises a *test* rail only while the capacitor is below a hardware test-voltage limit (proposed 100 V; the supervisor's own limit is 60 V). It never powers the patient relay coil. Permit and test permit together give neither.
11. **Bridge test steps** (`bridge_test_step`) under the test rail: each of the four switches commanded on and off into the internal test load (§B6.6), with a pass/fail and a measurement reported by the board layer. This drive must not set the sequence latch, and must be impossible without the test rail. **Question for the hardware designer**: is that separation practical, or should each switch test be its own short latched test sequence?
12. **Discharge paths timeable one at a time**: path A conducts when the main controller lets go, path B when the supervisor does (§B5.3, already so).
13. **The adult/child switch's second contact read back** by the main controller (`patient_mode_ceiling`), and the hardware ceiling falls back to the adult value when the contacts disagree (D-60).
14. **Front-end recovery.** Pad, heart and impedance readings must be usable again within `front_end_recovery_ms` (1.5 s, provisional) of the relay returning; the real figure must be measured.

## Choices made where the design documents were not specific

- **Charging during analysis (D-29): the state model.** A separate state, `AnalysingCharging` ("analysing and charging"), not a flag inside `Analysing`. It is what the main controller tells the supervisor, what the event record shows (with `ChargingDuringAnalysis` and `ChargeStarted` events), and what the simulator timeline prints, so "analysing and charging" is never ambiguous. The supervisor holds in it but can never permit from it. `Analysing` (no charging) is kept for `Config::charge_during_analysis = false`, so the earlier design can be measured from the same code. "Shock" when already charged goes straight to `Countdown` ("Shock advised. Stand clear. Three, two, one."); "shock" while still charging goes to `Charging` ("Shock advised. Charging. Stand clear.") and on to `Countdown` the moment the charge is reached. The charge time limit counts from the start of the analysis.
- **Emptying is background work, not a blocking state.** The old `Disarming` state is gone. On "no shock", "not sure" to the limit, cancel, pads off, an abandoned shock, after a shock, and on any fault, the device lets go of the capacitor (which empties by itself, discharge by default) and gives its next instruction at once. It then checks every tick that the capacitor is empty: its own reading, and a supervisor report sent after emptying began (so that the supervisor's own "charged too long" timer has also reset), within the 3 s limit; if only the supervisor's confirmation is missing at the limit, its own reading is enough. Until then it holds nothing and starts no new charge. If its own reading is not empty by the limit, the serious fault follows from whatever state the device is in. Why: with charging during analysis every "no shock" cycle has a full charge to burn off (up to about 0.8 s in the model); making the responder wait for that before "Start CPR" would add hands-off time to every non-shockable cycle and to every shock.
- **Adult/child switch moved during the analysis (with charging):** the capacitor is emptied and charged again for the new mode, and the analysis carries on. It is not sent to CPR: a switch moved while the pads are going on is most likely a correction, and two minutes of CPR before the next analysis would cost a child in VF far more than the second it takes to empty and recharge. Once a shock has been advised, a switch change still abandons the shock (as before).
- **How fresh "still shockable" must be.** At delivery the latest rhythm decision must be "shockable", no older than 5 seconds (provisional), and no other answer may have arrived since the shock was advised. A single "not shockable" or "not sure" at any point after that stops the shock, even if later answers say "shockable" again.
- **Cancel during the power-on self-test is ignored** (D-31) by both controllers: a stray press while the device is drawn and switched on must not disable it. After the self-test a press that is still held counts as cancel, as in every other state.
- **Stuck cancel (D-31).** A cancel that reads pressed without a break for 10 s (`Config::cancel_stuck_ms`, provisional) is a stuck-button fault, with its own event and prompt, on either controller's own view of the button (the supervisor latches `SupervisorFault::CancelStuck` and sounds its alarm). A rule "pressed from switch-on to the end of the self-test" alone was not used: the self-test takes well under a second, so it would turn a brief stray press into a permanent fault. Like every fault it is final until power-off.
- **Pads above the shock range (D-32).** Pads count as on from 25 to 250 Ω (`aed_types::pads_sensed`); the shock range stays 25 to 175 Ω (`aed_types::in_shock_range`) for the planner and the supervisor. Between the two, the device charges during the analysis as usual (so a shock can follow at once if pressing the pads brings the resistance into range, and the shock is still blocked if it does not), says "Press pads firmly to bare chest." as the analysis starts and every 15 s during CPR, but never during the hands-off and stand-clear phases, and at delivery either shocks (in range) or says "Poor pad contact. No shock." and "Start CPR.".
- **Pads off after a shock was advised (finding F-6):** "Check pads." then "Attach pads to bare chest.", straight to the attach-pads state; with the pads off the device can neither analyse nor shock, so re-attaching them is the one instruction. If the fresh reading taken for the shock plan already shows the pads off or shorted, the device takes it as pads off at once.
- **Consent during the shock (D-59): which failures are faults.** A sequence that never starts (no permit, the rail never rises, the relay does not reach the bridge, the bridge does not start, the hardware's permit cap) is "Shock not delivered", CPR, and the next analysis tries again: it is like a shock the supervisor does not permit, and a fault would end every later chance of a shock. A sequence the hardware ended by its time cap or over-current trip, a capacitor that fell to a level no plan explains, or a relay that does not come back, is a fault: the output stage did something other than the plan, or the pads stay on the bridge. A completed sequence that left the capacitor almost full ("not delivered", for example pads that came off at the last moment) is not a fault. The supervisor applies the same rule independently and latches a fault for the hardware trips and implausible falls only. An unused permit is recorded by the supervisor, not latched: the hardware's own permit cap is the backstop.
- **The adult/child switch's contacts disagree (D-60): "not ready", not an advisory prompt.** D-60 says the device reports "not ready", and that is what it does: the ready indicator goes off and the event is recorded, and a periodic test fails with its own code. In a rescue it says nothing aloud and carries on with the primary contact's mode, because the responder cannot fix a contact and the hardware ceiling falls back to the adult value, so shocks remain possible in either mode.
- **A shock the supervisor does not permit** (the request times out) is recorded as not delivered, the capacitor is emptied and the device goes to CPR and tries again at the next analysis. It is not a fault on its own; the supervisor's own latched faults cover persistent problems.
- **Every supervisor fault is latched until power-off**, including the main controller's heartbeat stopping. A main controller that restarts mid-rescue therefore cannot shock again until the device is switched off and on.
- **Pad contact is smoothed** (200 ms) before the device acts on it, but the shock plan always uses a fresh, unsmoothed reading, and the supervisor checks its own reading.
- **Expired or missing pads** found by the self-test are a warning, not a fault, so the rescue continues.
- **"Not sure" while analysing is not final** (finding F-1). Compressions running on into the analysis are the usual cause, so the device says "Do not touch the patient. Still analysing." (at most every 3 s) and keeps looking. Only "shock" or "no shock" ends the analysis early. At the analysis time limit (12 s) with only "not sure" answers, the device says "Unable to analyse. No shock." and "Start CPR." While armed, any "not sure" still stops the shock.
- **Two voltage tolerances, not one** (finding F-2), set from D-28 (sensors accurate to ±1 % ± 7 V). *At the planned voltage*: a controller's own reading within 1 % + 12 V of the plan counts as charged and stays armed; both controllers check their own reading this way. *Agreement*: each sensor may be off by 1 % + 12 V (7 V sensor, 1 V rounding, 4 V for a slightly old reading), so the two readings agree while they differ by no more than twice that (at the higher reading). The arithmetic is on the `Config` fields. "Empty" is only reported when the reading is below 50 V by a full sensor allowance (about 37 V or less). Residual risk: during a fast charge on a slow message wire (tens of ms of delay), with both sensors at opposite ends of their accuracy, the 10 V margin left for a stale reading is thin; the 500 ms persistence time covers it only because each fresh status message brings the readings back into agreement. The overvoltage limit (2,200 V) stays a hard limit on each controller's own reading. The planner's charge voltage must match the charge target exactly (both are nominal numbers, not readings).
- **The charger is cut off whenever the discharge path is active** (finding F-3). This is a requirement on the future hardware, written down in `interlock::charger_may_run`. The main controller also only asks for the charger once the supervisor reports it is holding, and the self-test waits for that before its charge step.
- **The supervisor has its own fault alarm** (finding F-3): a buzzer and light it alone drives, on whenever it has a latched fault, and also if the main controller never sends a single message within 1 s of switch-on.
- **Power-on self-test charges to 400 V**, not full energy, so switching on in an emergency is not delayed. The full-energy test (D-15) is the same sequence given the full voltage, for periodic checks. The charge step's time limit is the full 12 s limit scaled by stored energy (voltage squared, relative to 2,000 V), with a 1 s floor: 1 s at 400 V, 11.4 s at 1,950 V (finding F-7).
- **The charger is asked for only on a supervisor report that arrived after the current charge was asked for**, not one left over from the self-test or an earlier charge. (A defensive extra: the hardware rule already stops the charger while the supervisor is not holding, and the mock board's instant message wire cannot show the difference.)
- **The Fault state is final** (as in the diagram), but keeps the metronome running and repeats "continue CPR".
- **Compression sensing (D-36) is a third type parameter.** `Rescue<A, P, C = NoChestSensor>`: `Rescue::new` builds one without it (exactly the earlier behaviour); `Rescue::with_chest_sensor` takes any `aed_types::ChestSensor` (the real one is `aed_cpr::CompressionDetector`). Impedance samples arrive through `Rescue::on_impedance_sample`, like heart-signal samples. `Config::chest_sensing` switches it off so the effect can be measured.
- **How the analysis is kept to a still chest.** Heart-signal samples are passed to the analysis only while the chest state is `HandsOff`; the moment it is `Compressing` or `Unknown` the analysis is reset (and its pending answer and latest decision dropped). So each decision is made from a stretch of still-chest signal, apart from the sensor's onset latency (median 0.33 s on real recordings): the few hundred milliseconds before a compression is recognised can be in the window. If a "shock" answer were reached inside that gap, the shock is still held back by the next rule. The analysis time limit (12 s from the start) is unchanged.
- **Armed states: hold back and analyse again, once.** A shock must never be given while compressions are sensed (finding F-11 asks how strict the countdown is; this is stricter in one direction only). Aborting to CPR would cost the patient a shock for two minutes because of one touch, so the device empties the charge and analyses again at once, which costs about 7 to 10 s; a second hands-on abort in the same cycle goes to CPR, so a responder who will not stop is not kept in a loop with neither CPR nor shocks. The charge is emptied rather than kept so that "charged too long" limits on both controllers keep their meaning. The supervisor is unchanged and is given no compression signal: its job is to stop a faulty main controller shocking without an advice, and a second compression detector inside it would be a new single point that could block every advised shock. Known gap: if the supervisor had already given its single permit when the hold-back happens (a window of about 200 ms in Delivering), the re-analysed shock is refused as "permit already used" and the device says "Shock not delivered" and goes to CPR.
- **A failed sensing channel degrades, it does not fault.** "Cannot tell" holds every analysis, so a dead channel would stop every shock; faulting would do the same. SAFETY.md requires that no single fault blocks an advised shock, so after 5 s of a channel problem with the pads on the device records `ChestSensingFailed` and carries on from the heart signal alone (the earlier behaviour, with `aed-rhythm`'s compression rule still in place). The cost: during that time finding F-12 is back. No spoken prompt is added (prompt load); the event record carries it.
- **Skipping the settling second once the chest is confirmed still (D-47).** The rhythm analysis's filters now run through CPR and while compressions hold an analysis back (`RhythmAnalyzer::track`). When compression sensing reports a good signal and "hands off", the analysis starts a fresh window at once on those settled filters (`RhythmAnalyzer::restart_window`, which the `aed-rhythm` analyser follows with a 0.25 s guard), recorded as `FreshAnalysisWindow` and counted in `Counters::fresh_windows`. Only two moments use it: the start of an analysis after CPR, and hands coming off during an analysis. Everything else keeps the full `reset()`: pads just attached (the filters have not seen this patient), after a shock (the front end saturates), a device without sensing or with it switched off, a failed channel, "cannot tell", or a signal that is still settling. The analyser itself also keeps whatever is left of a full second's settling after its last full reset, so a hands-off moment soon after a reset still waits for it. With sensing off nothing changes at all: the filters are run during CPR, but every analysis starts with a full reset that forgets them.
- **Periodic self-test (D-15), in `schedule`.** The device has no real-time clock; a low-power timer in the power domain counts seconds while it is off and wakes it. `TestSchedule` is pure logic: woken with the time and the conditions (in use, on the dock, temperature, battery), it answers "run the daily check", "run the full-energy test" or nothing, and when to wake next; it is told every result. Due times stay on a fixed grid (counted from when a test was due, not when the timer woke), so late wakes do not shift them, and a test missed by more than its interval runs once and starts a new grid (no burst of catch-up tests). A timer that goes backwards, or that the board reports restarted, makes both tests due and the device "not ready" until they pass. `PeriodicTestRun` runs one test with the same `SelfTest` sequence as switch-on, at 400 V or at the adult shock voltage, with the supervisor holding as at switch-on, and then confirms the capacitor is empty. Decisions (provisional, Claude): a test due while the device is in use waits, and the daily check runs at the first wake after use; tests run on the charging dock (a device that lives on its dock must not go untested; the power design must let the test load come from the battery while docked); outside 0-45 °C, or with a battery that is not good, only the full-energy test waits; a test not passed for its interval plus one grace day is counted missed and shows "not ready"; a failed daily check is retried after 1 h, a failed full-energy test after 1 day (every full test wears the capacitor); a daily pass does not clear a failed full-energy test, a full pass clears both; pads missing or expired, or a low battery, show "not ready" although the hardware passed; a capacitor not confirmed empty sounds the alarm and stops all automatic tests until service, because each test would charge it again. Full-energy charges are counted, and rescue charges can be added, so capacitor wear is visible; the counts and the readiness go into the rescue's event record at switch-on (`Rescue::record_standby`, `Event::StandbyRecord`). **A device shown "not ready" still runs a rescue**: its own switch-on self-test decides as before; if it passes the device analyses and shocks with every usual check in place, and if it fails the device guides CPR. Blocking the rescue on an earlier periodic result would turn one failed test, possibly cleared since, into a certain "no shock"; the responder is not told (no spoken prompt is added).
- **Compressions have their own record.** About 220 compressions per CPR period would push safety events out of the 256-entry event record, so each compression goes into a separate 512-entry `CompressionLog`; the event record gets pauses (2 s or more) and one summary per CPR period.

- **Heat (D-41, D-48, D-51, D-52, D-53), in `heat`, `standby`, `readiness`.** Every figure is a `Config` field with its source. Choices made here (Claude, 27 November 2026, for the owner to confirm):
  - *Which readings to trust.* A reading is not used when it is missing, outside −40 to +100 °C (R-H1's readable range), unchanged for an hour of wakes while another sensor moved 3 °C, or more than 15 °C from the median of the others (provisional; the box's inside evens out with a 25-minute time constant, and no sensor sits on the discharge resistors). With two readings left that disagree, both are distrusted.
  - *Unknown temperature.* Outside a rescue it counts as too hot: no test charge, no dock charging, and "not ready". **In a rescue it does not block a shock**: a point without a trusted reading takes the hottest trusted reading plus 5 °C, and with nothing trusted at all heat does not hold the shock back (recorded as `TemperaturesUnknown`). Treating unknown as too hot in a rescue would turn one failed sensor, or a failed sensor bus, into "no shocks" for every patient, which SAFETY.md §4 forbids; this mirrors D-38.
  - *Rescue while too hot (D-51).* The switch-on self-test skips only its charge steps (it charges to 400 V) and still checks the battery under load, the supervisor link and the pads; the device says once "Device too hot. Shocks delayed until it cools."; every analysis runs without charging; a "shock" answer gives "Shock advised. Device too hot to charge." and "Start CPR." at once (never silence); the next analysis is after the normal CPR period. **It never charges during CPR**, even once it has cooled: a charge held through CPR would outlast the 25 s "charged too long" limits of both controllers (so either the limits or the supervisor's hold rules would have to change), a charged capacitor under hands that are pressing on the chest has no stand-clear warning, and in normal operation the device is only charged while it has asked for hands off. With charging during analysis, a device that has cooled loses nothing at its next analysis. The cost is up to one CPR period (2 minutes) between cooling and the next chance to shock (simulated: switched on at 63 °C into 25 °C air, cool enough after about 2.4 minutes, shocked at 4.7 minutes). Whether to cut a CPR period short once the device has cooled is a question for the owner and a clinician.
  - *When the limit is checked.* When a charge would start, and throughout an analysis that charges (crossing it lets the charge go and the analysis continues without one). Once a shock has been advised the charge continues to the shock; only the supervisor's own 65 °C backstop can stop it then. A capacitor warms by a fraction of a degree in one cycle, so this matters only at the edge.
  - *Pre-charge limit (55 °C).* Above 55 °C the device does not charge during the analysis (D-29) but only once a shock is advised (about 6 s more hands-off time before a shock). Every no-shock analysis otherwise burns a whole charge inside the device (about 253 J of heat, parts study §4). Simulated: in a 57 °C car with the device at 58 °C, 20 minutes of asystole took the device to 60.1 °C with charging during every analysis (and VF at minute 20 was then held back three times); with this rule it stayed at 58.2 °C and the VF was shocked.
  - *The supervisor's check.* Its own sensor on the capacitor; above 65 °C (60 °C plus two sensors' ±2 °C and 1 °C) it lets go of the capacitor and refuses a permit, without latching a fault or sounding its alarm, and reports `too_hot` so the main controller says "Device too hot. No shock." and goes to CPR instead of faulting. **So that it cannot become a single fault that blocks every shock**: a reading that is missing or out of range is ignored; and a reading over the limit but more than 15 °C above the main controller's own reported temperature is ignored (one of the two sensors is wrong; the main controller's five sensors decide). The main controller also includes the supervisor's reading in its own judgement, where the median check distrusts a supervisor sensor stuck high. Residual risk: a main controller whose own sensors all read low by more than 15 °C AND which ignores heat would charge a hot capacitor.
  - *Was above 70 °C, has cooled.* D-50 is applied as for any "not ready": if the switch-on self-test passes, the device shocks with every usual check and says nothing about it. Reason: the likely damage (lost capacitance, a weakened battery) degrades a shock rather than making it dangerous, the switch-on self-test loads the battery and the charge limits still apply, and refusing would be a certain "no shock" for a patient in VF. A question for the owner.
  - *Logging.* On the self-test timer (`Standby::on_wake` asks for the sooner of the two next wakes): every 5 minutes up to 40 °C, every minute above (R-H2). One record entry per hour (hottest and coolest trusted reading, number of wakes, flags), 2,160 entries (90 days, about 26 KB of memory that survives power loss). When full, the oldest entry is overwritten, but every reading has already gone into the lifetime totals (hottest and coolest overall and per sensor, time above 40, 50 and 60 °C, episodes, gaps), so the peak is never lost. A wake more than 5 minutes later than asked, or a timer that restarted, is a gap: recorded, and "not ready" until a self-test passes (made due at once). The temperature in a gap is unknown, so the gap does not add to the pad heat total (it is flagged instead).
  - *Pad heat (D-52).* Time between two wakes counts as hot if the pad point read above 50 °C at either end (conservative); a failed pad sensor takes the hottest reading plus 5 °C, and unknown counts as hot. A new pad set is recognised by an identity the pad connector reports (`StandbyInputs::pad_set_id`; a requirement on the made-to-order pad connector, parts study B3), so the same pads taken out and put back keep their total; `Standby::pads_replaced` is the fallback for a connector without one. Heat-worn pads are `PadCartridge::HeatWorn`: advisory in a rescue ("Pads heat damaged. Replace pads after use.").
  - *Capacitor wear (D-53).* `CapacitorWear` counts full-energy test charges and rescue charges (one per arming, `Counters::capacitor_charges`) and survives power loss. "Service soon" from 90 % (advisory, the indicator still shows ready); "service due" at 2,500: "not ready", but **the device still shocks**, because a worn film capacitor degrades gently and each self-test and each charge still checks that it reaches its voltage. **The weekly full-energy test continues past the life**: it adds about 52 charges a year (2 % of the life), and it is the only check that a worn capacitor still holds full energy.
  - *What survives the battery being taken out.* The heat record, the latches, the pad heat total and the wear count (`DurableStore`, written by the board after every wake). The self-test schedule stays in memory kept alive by the power domain, as before; after a power loss it starts again (not ready until both tests pass) and the heat record shows a gap. A durable record that cannot be read back is "not ready" (`RecordLost`) until a service action.
- **Record download (D-09).** `export::write_record` streams a plain-text record through any `core::fmt::Write` (the dock contacts' serial line; no buffer needed): a version line, readiness and every reason, wear, test counters, heat state, pad heat, lifetime totals, per-sensor extremes, the heat record and the last rescue's event record, ending with a CRC-32. The format is documented in `src/export.rs`; `aed-sim` has an independent reader (`aed_sim::record`). There is no radio code in the firmware; a Bluetooth module is a later option (D-45).
